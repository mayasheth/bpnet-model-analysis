## Results that matter

**DNase input beats ATAC and survives transfer (F-010).** Top-quintile Pearson: in-cell K562
0.736 vs 0.699 (+0.037 [+0.019, +0.056]); in-cell GM12878 0.671 vs 0.585 (+0.086); transferred
K562 to GM12878 0.574 vs 0.531 (+0.043). Transferred DNase clears GM12878's own ATAC-only floor
by **+0.056 [+0.014, +0.099]**, *p*=0.020, where the ATAC-input model manages +0.013 (*p*=0.25).
Nothing else in the project has cleared a target cell type's floor on transfer. The depth
confound runs *against* this: DNase is the shallower input in both cell types.

**p300 as an ABC activity term works in K562 but does not deploy (F-008, F-009).** Predicted
p300 beats the ATAC-only floor by +0.055 [+0.034, +0.074] on a paired bootstrap and matches
measured H3K27ac. Observed p300 beats observed H3K27ac by +0.038. But GM12878-trained p300
applied to K562 is +0.009 (*p*=0.72). Transfer is asymmetric: K562 to GM12878 retains +0.207
over the target's floor, GM12878 to K562 retains nothing, and both models are equally strong at
home (+0.313, +0.309).

**Predicted H3K27ac never clears the benchmark floor (F-004).** Best arm +0.025 [-0.003, +0.052]
paired. Confirmed by paired re-test, not just the unpaired intervals.

**DNase has a base-resolution profile, H3K27ac does not.** 1 bp top-quintile ceiling 0.848
(K562) and 0.686 (GM12878) against 0.21 and 0.18 for H3K27ac. This unblocks the converter.

## What didn't work, and the bugs

- **`bedtools merge` to pool bedGraphs is wrong and silent.** `genomecov -bg` emits bookended
  intervals, so merge fuses runs and sums values. Produced a DNase track with 34x the correct
  signal, exit 0, valid-looking bigwig. Ten GPU folds launched against it before the totals gave
  it away. Pool by merging BAMs and calling `genomecov` once, as `0.31` already did.
- **`bpnet-gc-background` fails two ways silently.** Exits 0 writing a 0-byte file when
  `bedtools` is absent from its env; hangs forever rather than reporting a shortfall when the
  foreground is GC-rich enough to exhaust high-GC bins (93% in 15s, then nothing for 2h). Fix:
  append the pixi env to PATH, subsample the foreground to 50,000, wrap in `timeout`.
- **The ABC snakemake driver stalls after its last real rule.** Three runs in a row: every child
  COMPLETED, nothing queued, driver idle indefinitely. Outputs were always fine. Gate downstream
  work on the consumed files (`gzip -t` plus row count) and cancel the driver.
- **Aggregate statistics misled me four times.** Peak overlap vs quantitative signal;
  residualised error at a stratum defined by accessibility disagreement; fold elevation without a
  dynamic-range control; a pooled RPKM mean read causally. All four are written up in report 2
  with the attributable-fraction test that catches them.
- **My own n annotations were wrong.** `n_label(n=len(d))` reported the summary table's row count
  as an element count ("n = 14 elements"). Fixed on fig11 only. **Assume the same class of error
  in the other figures from that pass; I checked that annotations were present, not correct.**

## Key decisions

- Reports split on churn rate, not topic, so the stable parts become citable and only report 3
  moves.
- Paired bootstrap (`4.17`) for every benchmark comparison. The pipeline's unpaired per-predictor
  CIs are ~+/-0.05 wide against differences of 0.004-0.099 and resolve nothing.
- Verify a manipulation before reading its result, with the failure condition pre-committed in
  code (`0.29` for the GC match). This is what makes the GC-matched null a real answer.
- New arms go in their own ABC results directory. Adding arms to a finished run forces a Peaks
  re-stamp that invalidates every completed arm.
- Use the established tool rather than reimplementing: `bpnet-gc-background` for matching, the
  existing `0.31` pooling pattern. A second implementation would confound any comparison.
- Figures are left uniformly single-pass while the decision table quotes RC-averaged numbers. The
  gap is +0.002 to +0.016, tabulated in report 3's Methods; two of six affected figures have no
  `rc_*` table in the format their script reads.

## Gotchas

- `GRCh38.main.chrom.sizes` **includes chrM**. Any read-count denominator must be derived from
  that file, not a hardcoded `chr1-22,X,Y` regex. I got this wrong in both directions before
  fixing it.
- GM12878's DNase is 9.5% chrM against K562's 0.075%, and 53.8M usable reads against 301.1M.
- Never quote a validation metric from a training log. It is unstratified; a promising gain there
  vanished entirely on the top quintile.
- `MultiModalBPNet.forward()` does **not** add the count offset. A residual-trained model's raw
  output *is* the residual.
- p300 checkpoints predate the `mode` attribute; `4.1` handles it by setting `m.mode = mode`.
- Older model dirs lack `training_complete.json` and evaluators refuse them. Backfill with
  `1.7.backfill_training_complete.py`, which infers completion from the epoch log.
- Non-GPU work goes to the lab's `engreitz` partition.
- Ask Maya before any broad search. She usually knows the path. I wasted time twice concluding
  something did not exist from a search that missed it: the snakemake9 profile, and
  `gc_negatives.bed` (in `data/`, not `reference/`).
